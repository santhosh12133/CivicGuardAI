This document is the deployment runbook for the CivicFix monorepo.

## 1. Backend deployment on Render

The repository includes `render.yaml` and `backend/Dockerfile` so the API and PostgreSQL database can be provisioned from the repository.

### Deploy

1. Push the repository to GitHub.
2. Open Render and create a new **Blueprint**.
3. Select `santhosh12133/CivicGuardAI`.
4. Render detects `render.yaml`.
5. Review the `civicfix-api` web service and `civicfix-db` PostgreSQL database.
6. During the first Blueprint setup, provide `CORS_ORIGINS` when prompted.
7. Apply the Blueprint.
8. Wait for the API deployment to finish.
9. Open the generated API URL and verify `/health` returns a JSON response with `status: ok` and `database: ok`.

Render's Blueprint system supports connecting a service to Postgres with `fromDatabase`, and can generate secret values without committing them to Git. Keep credentials out of `render.yaml`. See the official Render Blueprint documentation for current platform behavior.

### Required Render variables

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `PORT` | `5000` |
| `API_PROTOCOL` | `https` |
| `API_HOST` | Automatically supplied from Render's external hostname |
| `DATABASE_URL` | Automatically supplied from Render Postgres |
| `JWT_SECRET` | Automatically generated by Render |
| `CORS_ORIGINS` | Your deployed admin URL, e.g. `https://your-admin.vercel.app` |
| `DB_SYNC` | `true` for the initial bootstrap because this repository does not yet use a migration runner |

After the first successful database bootstrap, plan a migration system and remove `DB_SYNC=true` for mature production operations.

### Important upload limitation

The current API stores uploaded photos in `backend/uploads` and exposes them through `/uploads`. A container filesystem is not a durable object store. For a serious production deployment, move uploads to S3-compatible object storage (or another durable object-storage provider) and store only the object URL/key in PostgreSQL.

## 2. Admin portal on Vercel

The admin portal is a Vite SPA and includes `admin/vercel.json` so client-side routes continue to work after a page refresh.

### Deploy

1. Create a new Vercel project from the GitHub repository.
2. Set the project **Root Directory** to `admin`.
3. Framework preset: Vite.
4. Build command: `npm run build`.
5. Output directory: `dist`.
6. Add the environment variable:

```text
VITE_API_URL=https://YOUR-API-DOMAIN/api
```

7. Deploy.
8. Open `/login` on the deployed admin URL.

The backend's `CORS_ORIGINS` must contain the exact deployed admin origin, without a trailing path, for example:

```text
https://civicfix-admin.vercel.app
```

## 3. Mobile deployment with Expo EAS

The mobile app now has `mobile/eas.json` with development, preview, and production profiles. Expo recommends assigning environment variables to the matching EAS environment and using `EXPO_PUBLIC_*` variables for values embedded in the client application.

### Configure the API URL

From the `mobile` directory, set the production API URL in EAS:

```bash
npx eas login
npx eas env:set --name EXPO_PUBLIC_API_URL --value https://YOUR-API-DOMAIN --environment production --visibility plaintext
```

Do not append `/api`. The mobile API client already calls paths such as `/api/auth/login` relative to the backend root.

For preview builds, configure the preview environment similarly:

```bash
npx eas env:set --name EXPO_PUBLIC_API_URL --value https://YOUR-STAGING-API-DOMAIN --environment preview --visibility plaintext
```

### Build Android/iOS

```bash
cd mobile
npm install
npx eas build --platform android --profile production
```

For both platforms:

```bash
npx eas build --platform all --profile production
```

EAS will guide you through signing credentials the first time. Production builds use the `production` EAS environment defined in `eas.json`.

## 4. Local development after deployment configuration

### Backend

```bash
cd backend
npm install
cp .env.example .env
npm run dev
```

### Admin

```bash
cd admin
npm install
cp .env.example .env
npm run dev
```

Set the admin `.env` value to:

```text
VITE_API_URL=http://localhost:5000/api
```

### Mobile

```bash
cd mobile
npm install
cp .env.example .env
npx expo start
```

Set `EXPO_PUBLIC_API_URL` to a URL reachable from the physical device. `localhost` normally points to the phone itself, not the development computer.

## 5. Production verification checklist

### API

- [ ] `GET /` returns the CivicFix API status.
- [ ] `GET /health` reports database `ok`.
- [ ] `NODE_ENV=production` is set.
- [ ] `JWT_SECRET` is at least 32 characters and is not committed.
- [ ] `CORS_ORIGINS` contains only trusted browser origins.
- [ ] HTTPS is enabled.
- [ ] Authentication works for citizen/staff/admin roles.
- [ ] A citizen can register and log in.
- [ ] A citizen can create an issue with a valid photo and location.
- [ ] Staff/admin can update issue status.
- [ ] Admin-only operations reject citizen tokens.
- [ ] Invalid JWTs return 401.
- [ ] Excessive requests receive 429 responses.
- [ ] Uploaded files are not publicly writable.

### Admin

- [ ] `VITE_API_URL` points to the deployed API `/api` root.
- [ ] `/login` loads directly.
- [ ] Refreshing `/dashboard` does not produce a Vercel 404.
- [ ] Staff/admin can log in.
- [ ] Citizens are rejected from the admin portal.

### Mobile

- [ ] Production EAS environment contains `EXPO_PUBLIC_API_URL`.
- [ ] The value points to the deployed API root and uses HTTPS.
- [ ] Login and registration work.
- [ ] Location permission works.
- [ ] Camera/gallery permissions work.
- [ ] Photo upload succeeds.
- [ ] Issue details load after creation.

## 6. Operational caveats

This repository is deployable, but deployment does not automatically mean the system is fully production-hardened.

Current items to address before a high-traffic public launch:

1. Move image uploads from local disk to durable object storage.
2. Replace the in-process rate limiter with Redis/shared rate limiting when running multiple API instances.
3. Introduce Sequelize migrations and stop relying on `DB_SYNC` for production schema management.
4. Add automated CI for backend, admin, and mobile checks before enabling unrestricted automatic deployments.
5. Add centralized logs, error tracking, uptime monitoring, backups, and database restore testing.
6. Consider HttpOnly secure cookies for browser admin authentication instead of localStorage tokens.
7. Run full integration tests against a real PostgreSQL instance and a deployed HTTPS environment before public release.
